# 161 D3D9Web Phase 4 — drop-in D3D9 COM/vtable to WebGL2

Date: 2026-07-19

> **IDirect3D9 capability follow-up completed by 162.** This document remains
> authoritative for the seven-slot COM/Present proof.

## Result

**VERIFIED in the local browser:** a packaged 32-bit PE named `d3d9.dll` was
loaded as Wine native at `0x10000000`. Its `Direct3DCreate9` export returned a
synthetic `IDirect3D9`; `CreateDevice` returned a synthetic
`IDirect3DDevice9`; the test then called the exact vtable slots for `Clear`,
`BeginScene`, `EndScene`, and `Present`.

Every HRESULT was `S_OK`. `Present` synchronously crossed the Phase 3 bridge,
drew the WebGL2 triangle on the existing shared 800x600 canvas, and returned
success. The test result and process exit were both clean:

```text
D3D9WEB_PHASE3_GL webgl2=1 triangle=1 canvas=shared size=800x600
D3D9WEB_PHASE4_COM create9=1 createDevice=0x00000000 clear=0x00000000 begin=0x00000000 end=0x00000000 present=0x00000000
D3D9WEB_PHASE4_RESULT=PASS
D3D9WEB_PHASE4_EXITCODE=0
```

The final confirmation run had no WINEDEBUG channels enabled. The retained DOM
had one canvas and no overlay.

## Loader finding

**VERIFIED:** naming a file `d3d9.dll` is insufficient under this Wine 1.7
root. Without a prefix DLL override, even explicit `LoadLibrary(".\\d3d9.dll")`
selected Wine builtin `C:\\windows\\system32\\d3d9.dll`, which then pulled
`wined3d.dll` and failed because the browser build has no usable OpenGL target.

Setting `WINEDLLOVERRIDES` inside `run_phase4_browser.bat` was also too late:
the Wine process and its module policy already existed. The working guest-side
setup is persisted before the client launch:

```bat
reg add "HKCU\Software\Wine\DllOverrides" /v d3d9 /d native /f
```

A one-run loader trace then directly recorded:

```text
Trying native dll L"C:\\files\\d3d9.dll"
Loaded L"C:\\files\\d3d9.dll" at 0x10000000: native
```

This registry setup must be part of the Azrok browser prefix/package contract.

## Implementation boundary

The new smoke DLL intentionally implements only:

- `Direct3DCreate9`;
- `IDirect3D9` slots 0/1/2/16;
- `IDirect3DDevice9` slots 0/1/2/17/41/42/43.

The current vtables leave every other slot null. This is safe only for the
synthetic smoke client, not for Azrok. It is therefore **not** an Azrok-ready
drop-in DLL and is not evidence that the Gate 1 method surface works.

The DLL uses a no-CRT `DllMain` build, but the earlier CRT build was not the
actual browser load failure: loader tracing proved the wrong builtin module was
selected. A native Windows `--load-only` control also passed `LoadLibrary` plus
`Direct3DCreate9` and exited 0.
