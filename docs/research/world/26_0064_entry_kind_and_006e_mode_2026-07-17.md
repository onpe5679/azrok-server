# S->C 0x0064 entry kinds, 0x006E mode, and the 0x00614865 crash (2026-07-17)

This note records a read-only Ghidra re-analysis of the state-1 entry reply.
It supplements `24_0064_datefix_and_ox_entry_2026-07-17.md`; live observations
remain the authority for scene identity.

## Directional separation

The two bytes which were previously both called "mode" are different fields:

- `C->S 0x0064 payload[0]` is a client-emitted status/request byte. The current
  live request value is `0x01`.
- `S->C 0x0064 payload[0]` is `entry_kind`. It selects an entry branch in
  `HandleS2C_0064_ApplyAuthoritativeSelf` (`0x00615650`).
- `S->C 0x006E payload[0]` is a separate persistent mode selector.

Therefore the same `C->S 0x0064 [01]` request can legitimately be answered
with different `S->C 0x0064 entry_kind` candidates. The request byte does not
prove that the reply should also begin with `0x01`.

## Accepted 0x0064 entry kinds

The handler accepts exactly `0x00`, `0x0A`, `0x0B`, and `0x14`. Any other
value bypasses the authoritative-self operation.

All four accepted values share the important work: applying selectors,
creating/reconciling the authoritative self actor, storing the actor ID,
applying coordinates and the clock block, and closing the loading screen.
Only `0x0A` and `0x0B` overwrite the pending local scene request:

| `entry_kind` | Static branch effect | Live evidence / disposition |
|---:|---|---|
| `0x00` | No pending-scene overwrite; common authoritative-self path only | Controlled five-`0x01`, `C->S 0x0064 [01]` run: stable OX |
| `0x14` | Same visible handler branch as `0x00` | Same controlled conditions: stable OX |
| `0x0A` | Sets pending scene code `0x2E`, clears four scene args, stores `(enabled=1, variant=0)` | Same controlled conditions: stable OX |
| `0x0B` | Sets pending scene code `0x2F`, clears four scene args, stores `(enabled=1, variant=1)` | Same controlled conditions: stable OX; the older crash was confounded |

The `(enabled, variant)` pair is stored by `FUN_00526e80` at game-manager
fields `+0x324` (byte) and `+0x325` (dword). This is a scene-request setting,
not the `S->C 0x006E` mode.

Static analysis proves only the `0x2E`/`0x2F` scene-code split. The statement
that `0x2E` is OX comes from the live render, not from a guessed symbol name.

## Historical confounded crash context at 0x00614865

The observed address `Azrok.exe+0x214865` is absolute address `0x00614865`,
inside `Hansol_Stage6Handler` (`0x00614720`). It is the third of four
unconditional stage-6 virtual calls:

```asm
00614842  call FUN_0050c190       ; returns protocol_root + 0x641
00614847  mov  [ebp-0x48], eax
...
0061485d  mov  edx, [ebp-0x48]    ; embedded subobject address
00614860  mov  eax, [edx]         ; load its vtable pointer
00614862  mov  ecx, [ebp-0x48]
00614865  mov  edx, [eax+4]       ; observed access violation
00614868  call edx
```

Because execution reached `0x00614865`, the embedded object address was
readable at `0x00614860`, but the vtable value loaded into `EAX` was null or
otherwise invalid. The immediate failure is therefore an uninitialized or
corrupted vtable for the `protocol_root + 0x641` subobject, not an out-of-range
`entry_kind` comparison.

The containing protocol-root constructor (`FUN_005110e0`) normally calls
`FUN_005b57a0(protocol_root+0x641)`. That subobject constructor explicitly
writes vtable address `0x006A7D6C` at offset zero. Its destructor also restores
that same vtable before invoking the base destructor. Consequently a bad
vtable at stage 6 narrows the possibilities to an incomplete/bypassed root
construction, premature lifetime teardown, or a later overwrite; the normal
constructor's intended default is not null.

The common `S->C 0x0064` path accesses this same subobject before stage 6:

- `FUN_005b61f0` converts payload `+0x1A` (seconds), writes timing-derived
  fields at subobject `+0xCB/+0xCF/+0xD4`, and calls an internal updater.
- `FUN_00614d40` reads the resulting `+0xD4` flag.
- Neither function constructs the subobject or writes its vtable.

Thus a valid date/seconds field can populate ordinary fields while leaving an
object-lifetime or overwrite fault unresolved. However, the later controlled
matrix ran `0x00`, `0x0A`, `0x0B`, and `0x14` with the same five-`0x01`
prelude and `C->S 0x0064 [01]`; every value reached stable OX. The old
`0x0B` crash therefore came from a different bootstrap/calibration condition,
not selector causality. The fault remains valuable evidence of an invalid
`protocol_root+0x641` object lifetime in that historical run only.

The highest-value debugger capture is therefore the register/object state at
the fault (`EAX`, `EDX`, `[EBP-0x48]`, and the dword at the returned
`protocol_root+0x641`). A hardware write breakpoint on the subobject's first
dword, armed after construction when it equals `0x006A7D6C`, would distinguish
later memory corruption/teardown from a constructor that was never reached.

## Actual S->C 0x006E behavior

`HandleS2C_006E_CommitReadyMode` (`0x006169D0`) consumes two bytes:

| Offset | Meaning | Effect |
|---:|---|---|
| `+0x00` | mode selector | On success, copied to two persistent subsystem fields |
| `+0x01` | ready/error gate | `0` commits; nonzero runs cleanup/error route `0x18` and does not mark ready |

For `[mode, 00]`, the handler queues event `0xC6`, writes mode to
`(gm+0x1889)+0x7B` and `(gm+0x22C4)+0x16B`, then sets its ready flag
`+0x129B = 1`. The mode is not merely a success boolean:

- The first stored copy is read as a dword. A downstream selector returns
  enum-like value `8` when mode is zero and `9` when it is nonzero.
- The second copy is read as a byte in an input/hit-test handler. When the
  cursor lies in either of two specific rectangles, a nonzero mode causes the
  handler to consume/accept the event early.

No direct read of either mode field was found in `Hansol_Stage6Handler`, and
the crash object at `protocol_root + 0x641` is different from both 0x006E
mode-bearing subobjects. Therefore `[00,00]` remains the least-assumptive
0x006E reply, and current evidence does not support changing its mode byte as
a fix for `0x00614865`.

## Controlled A/B result

Fresh-process tests reached a real `C->S 0x0064 [01]` after the same corrected
five-`0x01` prelude for all four candidates. `0x00`, `0x0A`, `0x0B`, and
`0x14` all produced stable OX. The earlier `0x00` and `0x14` observations that
never emitted `C->S 0x0064` are retained as superseded pre-selector timing
evidence, not candidate results. There is no longer a safety ranking among the
four accepted values on the basis of the historical `0x0B` crash.

## What entry_kind 0x00 retains

The global room request and the actor-local scene/action field are separate:

- Room code `0x6E` is already stored in `gm+0x31AAD` by
  `GameManager_EnqueueRoomCode` and drives the Hansol room/stage dispatcher.
- The current actor has a separate dword at `actor+0x107`. Its constructor
  initializes it to `0`; the stage-0 local bootstrap calls `FUN_00525a60`,
  which changes it to ordinary/default value `1` unless it is already special
  value `0x2E` or `0x2F`.

`S->C 0x0064 entry_kind=0x00` does not write `actor+0x107`. It therefore
retains the stage-0 default `1` while the global room request remains `0x6E`.
This is not a contradiction and no packet should copy global room code `0x6E`
into the actor-local field.

The same rule applies to the actor transition pair:

- actor construction initializes `actor+0x324 = 0` and
  `actor+0x325 = -1`;
- only `entry_kind=0x0A/0x0B` calls `FUN_00526e80` to change the pair to
  `(1,0)` or `(1,1)`;
- `entry_kind=0x00/0x14` retains `(0,-1)`.

The common 0x0064 path still authoritatively applies the self actor ID,
coordinates, appearance selectors, valid clock data, actor reconciliation,
and loading-close operation. Thus `0x00` means “apply self state without an
alternate actor-local scene transition,” not “skip self initialization.”


`0x00` remains useful as the least-mutating diagnostic value, but the
controlled result proves it is not a Plaza selector.

## Do not add remote-actor sync to the minimal self-entry test

Read-only analysis of the late-sync handlers narrows the minimal self-entry
reply to `S->C 0x0064` plus successful `S->C 0x006E [00,00]`. `entry_kind=00`
is the least-mutating diagnostic choice, not a proven Plaza selector.
The neighbouring packets are remote-actor maintenance, not missing self/world
initialization:

| Opcode | Actual target/effect | Relevance to a fresh single-player entry |
|---:|---|---|
| `0x0065` | No payload. Destroys/frees the staged remote-actor list and resets its auxiliary container. | Optional cleanup only; not a Plaza or self-ready trigger. |
| `0x0066` | Spawns `0x1A`-byte remote-actor records. `RemoteActor_EnsureFrom0066Record` immediately returns null when a record ID equals the authoritative self ID. | Omit unless real non-self actors must be shown. A synthetic self record is ignored. |
| `0x0068` | Applies `0x18`-byte state records to existing non-self actors. If the first record ID equals self, the handler returns before processing the batch. | A self-position draft is a no-op. Requires a real remote actor created by 0x0066. |
| `0x0069` | Handles self or an existing remote actor. For self with control dword `+0x0C == 0`, it applies an action record and forces `actor+0x107=1` when the prior value is not `0x2E/0x2F`; nonzero control skips the self update. | Redundant after 0x0064 coordinates and adds action-state side effects. Omit from the clean 0x00 test. |

`0x0066` does call a remote-list finalizer after its record loop, including for
an empty batch, but that object at `gm+0x31C78` belongs to remote/UI tracking;
no dependency from the Hansol stage-6 subobject or 0x006E ready flag was found.
Likewise, none of 0x0065/0x0066/0x0068/0x0069 constructs or repairs the
`protocol_root+0x641` vtable involved in the `0x00614865` crash.

If multiplayer/world population is added later, the coherent ordering is
`0x0065` (flush old remotes), `0x0066` (spawn real non-self records), then
`0x0068/0x0069` (state updates for those actors). That sequence should remain
outside the minimal self-entry experiment so it cannot mask the result.

## Packet-faithful C->S 0x0019 door response

The current server's `C->S 0x0019` handler directly writes both
`gm+0x31C71=1` and `gm+0x31C72=1`, then sends a proactive
`0x0003+0x0007+0x0005+0x000A+0x000B` bundle. This is not equivalent to the
original transition contract:

- `gm+0x31C72` is normally set by the client-side room transition routine.
- `gm+0x31C71` is the later calibration/load permission latch; it should be
  set when the fifth server `S->C 0x0004 [01]` sample is internally converted
  to `0xFF`, not pre-written at the door click.
- The original transition performs room enqueue and subsystem cleanup in
  addition to setting the flag.

`DispatchState0Common_S2C` proves the existing server-authoritative entry
point: `S->C 0x000D` with payload byte `0` calls
`Plaza_TransitionFromRoom @ 0x00568770`. A nonzero payload takes error route
`0x1C` instead. No other observed S2C packet is a simple, equivalent setter for
the whole transition.

`Plaza_TransitionFromRoom` performs this order internally:

1. enqueue global room code `0x6E`;
2. clean/reset several room subsystems through virtual calls;
3. set the Hansol transition flag (`gm+0x31C72=1`);
4. reset the calibration handler with a null sample.

This also unifies the two crashes. At `0x0056880F` the transition obtains the
same `protocol_root+0x641` subobject later used by Hansol stage 6, then invokes
its vtable slot `+0x0C` at `0x00568822`. Thus the old report that
`S->C 0x000D` crashes in a Plaza subsystem and the later stage-6 fault at
`0x00614865` point to the same invalid object/vtable lifetime. The memory
shortcut succeeds by bypassing these virtual cleanup calls; it does not prove
that their state effects are unnecessary.

## Minimal Data\Space\Plaza protocol contract

For a stable PatHouse process which emits `C->S 0x0019`, the minimal intended
packet-only sequence is:

1. `S->C 0x0003 [01] + "Data\\Space\\Plaza\\0"` to replace the space-root
   string before any `hansol.wmb` request is consumed. The handler stores the
   leading byte as a dword at `gm+0x31C63` and copies the NUL-terminated path
   from payload `+1`. No direct reader of `gm+0x31C63` was found; retaining the
   server's already-used value `01` avoids introducing an unrelated change.
2. After the path handler has returned, `S->C 0x000D [00]` to invoke the full
   transition, enqueue room `0x6E`, set `gm+0x31C72`, and reset calibration.
   Separate packets/ticks are preferable while diagnosing the vtable fault.
3. In response to the calibration exchange, send five paced
   `S->C 0x0004 [01]` samples. The fifth receive sets `gm+0x31C71` through the
   client's internal `0xFF` conversion.
4. Wait for natural `C->S 0x0064 [01]`, then reply with authoritative
   `S->C 0x0064 entry_kind=00` and `S->C 0x006E [00,00]`. Here `0x00` is
   chosen only to avoid the extra actor-local `0x2E/0x2F` transition; all four
   accepted entry kinds currently converge on OX under controlled conditions.

Do **not** include a fresh `S->C 0x0007` in this door response. `0x000D`
already enqueues `0x6E`; `HandleS2C_0007_EmitPostSetupStateRequest` would read
the newly set `gm+0x31C72` and enqueue `0x6E` again. Replaying the 472-byte
setup blob also re-enters broad zone/stat initialization and has an established
double-bundle crash history. Consequently `0x0005/0x000A/0x000B` are also not
part of the minimal door transition; they belong to the earlier zone setup.

If the temporary memory shortcut remains for a diagnostic run, its proactive
fallback requires `0x0003` strictly before exactly one `0x0007`, with matching
`0x0005` state and without `0x0002/0x0006`. That is only a compatibility
fallback. A genuinely packet-faithful replacement cannot be declared working
until the shared `protocol_root+0x641` vtable problem is fixed and
`0x0003 -> 0x000D -> calibration -> 0x0064/0x006E` completes without process
memory writes.
