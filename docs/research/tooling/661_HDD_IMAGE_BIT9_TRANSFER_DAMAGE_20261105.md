# 661 2011.img 비트 손상: 3/29 덤프 때 생긴 전송 오류이고, 같은 날 따로 복사한 설치본은 온전하다

Date: 2026-11-05

archive.org 업로드본을 꾸리다가 프로젝트 `Data\` 와 2011.img 에서 꺼낸 사본(`B:\azrok_2011_extract`)이
파일 721개에서 다르다는 것이 나왔다. 어느 쪽이 원본인지, 손상이 어디서 생겼는지 확정한다.

## 결론

- **VERIFIED (사용자 증언 + 산술):** 2011.img 는 3월에 찾은 그 하드 한 개의 전체 덤프다. 하드는 한 번만 연결했고 덤프도 한 번만 떴다(사용자).
  이미지 크기 80,060,424,192 B = 하드 라벨 LBA 156,368,016 × 512 와 정확히 같다. "다른 하드에서 7/18 에 나왔다"는 `CHRONICLE.md` 제4부 서술은 틀렸다. 7/18 은 이미지를 다시 분석한 날이다.
- **VERIFIED (파일 시각):** 같은 3/29 하루에 하드를 두 번 읽었다.
  | 시각 (3/29) | 사건 |
  |---|---|
  | 13:57 | 하드 사진 (`20260329_135706.jpg`) |
  | 16:38 | `D:\2011.img` 쓰기 끝 (mtime). D: 생성 시각은 17:00 이라 다른 곳에서 만든 뒤 옮긴 것으로 보인다 (INFERRED) |
  | 17:27 / 18:36 | `D:\DMDEs`, `D:\DMDEs2` (DMDE 복구 산출물) |
  | 19:06 | `D:\Azrok_Plaza` 설치 폴더 복사 |
  | 19:17 | 프로젝트 `Data\` 생성. `D:\Azrok_Plaza\Data\sun.fx` 와 해시 동일 (`C00DBCBECC6906A1…`) |
- **VERIFIED (80 GB 전수 스캔, 203 초):** `D:\2011.img` 안에 `sun.fx` 의 온전한 문자열 `Define your needed values` 는 **0회**,
  손상 문자열 `Fefine"your negdgd"vclwes` 는 **1회**(오프셋 `0x358167E6B`, 섹터 28,052,287) 나온다.
  손상은 7/18 추출 도구가 아니라 **이미지 파일 자체**에 있다. 그리고 19:06 사본은 이미지에서 나올 수 없다.
- **INFERRED:** 19:06 복사는 이미지가 아니라 연결돼 있던 하드에서 직접 읽은 것이다. 덤프(16:38 이전)와 폴더 복사(19:06)가 같은 연결 안의 서로 다른 두 번의 읽기였고, 덤프 쪽만 손상됐다.
- **VERIFIED (721 파일 전수):** 다른 바이트 36,622,549 개가 **전부 홀수 오프셋**이다(짝수 0). 전부 비트 `0x02` 만 다르다.
  이미지 쪽이 비트를 켠 경우 35,938,570, 끈 경우 683,979 (98:2).
- **INFERRED:** 16비트 워드의 상위 바이트 비트 1, 즉 비트 9 한 가닥만 흔들린 것이다. 디스크 표면 손상이면 섹터 단위로 읽기 실패나 ECC 오류가 나지 이런 모양이 나오지 않는다.
  IDE 데이터선(DD9)이나 USB-IDE 변환기 같은 **전송 경로의 한 가닥**이 덤프 도중 일부 구간에서 불안정했던 것으로 본다. 하드 자체는 멀쩡할 가능성이 높다 (NOT VERIFIED).
- **VERIFIED:** 손상은 구간성이다. 같은 이미지에서 꺼낸 네이버판 `Setup.zip` 은 항목 2,558개의 CRC32 가 전부 맞는다.

## 어느 사본이 원본인가

- **VERIFIED:** 721개 중 537개는 네이버판 `Setup.zip`(CRC 정상) 안에도 있고, 537개 전부 프로젝트 사본과 같고 이미지 사본과는 0개 같다.
- **INFERRED:** 나머지 184개도 같은 홀수 오프셋·0x02 패턴이므로 이미지 쪽이 손상이다.
- 따라서 프로젝트 `Data\`(= `D:\Azrok_Plaza`)가 원본이다. archive.org 업로드본은 이 사본을 쓴다.

## 별마루

- **VERIFIED:** 프로젝트 `starmaru\` 는 이미지 사본과 손상까지 바이트 동일하다 (260/260). 생성 시각 2026-04-01 03:43, `D:\DMDEs2` 마지막 수정 04-01 03:27.
- **INFERRED:** 별마루는 3/29 에 하드에서 직접 복사하지 않았고, 4/1 에 이미지에서 DMDE 로 꺼냈다. 그래서 덤프 손상을 그대로 물려받았다.
- **VERIFIED (파일별 MD5, 2026-11-05):** `version.dat` 은 `[이름][0x00][크기 u32][MD5 16B]` 레코드 목록이다. 그 자체도 홀수 바이트가 손상됐지만 짝수 바이트는 온전하므로,
  각 파일 MD5 의 짝수 위치 8바이트(64비트)를 엄격 비교하고 홀수 위치는 0x02 차이만 허용해 대조했다.
  | 판정 | 개수 | 내용 |
  |---|---:|---|
  | 온전 (MD5 일치) | 199 | `starmaru.exe`, `open.exe`, `d3dx9_36.dll`, `data.dat`, `skin001/002.skn`, `bar/bg/cancel.uit` 포함 |
  | 손상 (MD5 짝수 바이트 0~1/8 일치) | 54 | 말풍선·알림창 UI 11, goods2D 11 (`action001~006`, `car001`, `chair001~003`, `fence001`), `.x` 17, `.dat` 6, `.dds` 9 (`tile3D` 3 포함) |
  | 목록 밖, 별도 확인 | 7 | `d3dx9_31.dll` 은 Windows SysWOW64 사본과 SHA-256 동일, `autoLauncher.dll` PE 구조 정상, manifest 2개 미확인, `license.txt`·`version.dat`·`uninst.exe`(PE 깨짐) 손상 |
  합계 손상 57개, 온전 확인 201개, 미확인 2개.
- **VERIFIED (Data 721개 기준 손상 밀도):** 손상 파일 안에서 바뀐 바이트는 전체의 20.8%, 파일별로 홀수 바이트 중 바뀐 비율 중앙값 34% (최소 0.1%, 최대 99%). 손상 파일도 통째로 날아간 것이 아니라 홀수 바이트의 비트 하나씩만 틀렸다.
- **NOT VERIFIED:** 하드를 다른 케이블·변환기로 한 번 더 연결해 `Program Files\starmaru` 만 다시 복사하면 온전한 사본을 얻을 수 있는지.
