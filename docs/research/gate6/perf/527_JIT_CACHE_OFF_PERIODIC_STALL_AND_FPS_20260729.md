# 527 주기적 정지의 원인은 `jitCacheUrl=off` — 계측 설정이 성능을 4배 깎고 있었다 (2026-07-29)

날짜: 2026-07-29
선행: #525 (정지를 호스트 쪽으로 특정), #526 (버퍼 축 시도·무효), #257
원본 실행파일·게임 자산·런타임 바이너리 무수정. 이 카드는 **URL 파라미터 하나**의 이야기다.

## 1. 결과 (leg 1회, 확인 A/B 진행 중)

같은 root·앱·런처·채택 스템, **`jitCacheUrl` 만 다르게** 측정했다.

| 지표 | `jitCacheUrl=off` | **기본값(캐시 켬)** |
|---|---|---|
| fps | 34.2 | **135.64** |
| 정지 횟수 / 60초 | 17 | **3** |
| 정지 간격 중앙값 | 3,150 ms | **17,451 ms** |
| 정지 길이 중앙값 | 76 ms | 62 ms |
| 무음 콜백 | 0.21% | 0.71% |

**fps 4.0배, 정지 빈도 1/5.7.** 목표 50 fps 를 크게 넘는다.

무음은 0.21% → 0.71% 로 오히려 늘었으나 콜백 1407 회 중 3 회 대 10 회로 표본이 작다.
확인 A/B 에서 재현되는지 봐야 한다.

## 2. 왜 이것이 정지를 만드는가 (INFERRED — 기전은 미확정)

캐시가 꺼져 있으면 BoxedWine WASM JIT 이 게스트 코드 블록을 **실행 중에** 컴파일하고
모듈을 등록한다. 등록 경로(`_wasm_jit_mt_register`, 모듈 브로커, `wasmTable.grow`)는
워커 쪽에서 돌고, 그동안 게스트 스레드가 멈춘다.

#525 에서 관측한 성질들이 이 그림과 전부 맞는다.

- 정지 주기가 **벽시계가 아니라 프레임에 묶여** 있었다(약 87~91 프레임).
  "새 코드 경로를 만날 때마다" 로 자연스럽게 설명된다.
- 메인 스레드 `longtask` 0 건, LoAF 무귀속. 정지가 메인 스레드 JS 가 아니었다.
- 메인 스레드 프로파일에서 정지 구간의 **90% 가 `(program)`** 이고 샘플 공백이 0 이었다.
  메인 스레드는 막힌 게 아니라 **바빴다**. 같은 프로파일에
  `__emscripten_thread_mailbox_await` 가 잡히는데, 메인 스레드에서는 `Atomics.wait` 가
  금지라 스핀 대기가 되고 그것이 `(program)` 으로 계상된다.
  → **실제로 멈추는 것은 워커이고 메인 스레드는 그것을 기다리며 헛돌았다.**

배제된 것들(전부 VERIFIED):

| 가설 | 근거 |
|---|---|
| 셰이더 컴파일/링크 | 14.4 초간 1 ms 이상 WebGL 호출 **0 건** (`linkProgram`/`compileShader`/`texImage2D`/`bufferData`/`readPixels`/`finish` 래핑) |
| 메인 스레드 wasm 컴파일 | `WebAssembly.Module`/`Instance`, `wasmTable.grow`, `addFunction` **0 건** (단, 훅이 메인 스레드 전용이라 워커 쪽은 배제되지 않았다) |
| IndexedDB 동기화 | `storage=memory` 로 불변 |
| 힙 증가 | 측정 구간 증가 **0 회** |
| 긴 JS 태스크 | `longtask` 316 초간 0 건 |

## 3. 이 카드가 무효화하는 것 (중요)

**2026-07-29 세션에서 낸 fps 수치는 전부 `jitCacheUrl=off` 에서 측정됐다.**
leg 템플릿(`run_leg.ps1`, `run_leg2.ps1`, `stall_leg.ps1`)이 그 값을 하드코딩하고 있었고,
그 값은 원래 **구버전 런타임이 "JIT 그룹 캐시 준비 중" 에서 멈추는 문제를 우회하려고**
쓰던 것이다. 채택 스템에는 해당하지 않는 설정인데 그대로 승계됐다.

따라서 #525 · #526 의 fps 수치(34~37 fps)와 "정지가 벽시계의 5~6%" 같은 서술은
**캐시 꺼진 조건의 값**으로 읽어야 한다. 정지의 존재와 오디오 드롭아웃의
1:1 대응(#525 §6)은 그대로 유효하지만, 그 크기와 빈도는 이 조건에 딸린 값이다.

`stall_leg.ps1` 에 `-JitCache` 파라미터를 추가했고, 빈 문자열이면 URL 에서
`jitCacheUrl` 을 아예 빼서 **페이지 기본값**을 쓰도록 했다.

## 4. 운영 지침

- 성능을 재거나 실제로 플레이할 때 **`jitCacheUrl=off` 를 쓰지 말 것.**
  진단 목적으로 캐시를 꺼야 할 때는 그 사실을 결과에 반드시 명기한다.
- leg 마다 **새 브라우저 인스턴스**로 시작하고 `msedge` 워킹셋을 함께 기록한다(#526 배너).

## 5. 미결

- 확인 A/B(캐시 켬/끔, 각각 새 브라우저) 재현 여부.
- 캐시를 켜도 남는 정지 3 회/60 초(62 ms)의 정체.
- 무음이 0.21% → 0.71% 로 는 것이 실재하는지, 표본 잡음인지.
- 135 fps 가 지속되는 값인지, 씬/조건에 딸린 값인지. 목표 "50 fps" 의 정의도
  여전히 미정이다(지속 vs 초기 창).
