# 525 BGM 끊김의 주원인은 계측 자체였다 — 디코드 실시간 배속 측정 (2026-07-29)

날짜: 2026-07-29
선행: #524 (pcre2 탐색 경로 수정으로 크래시 해결), #523, #250, #249, #248
원본 실행파일·게임 자산·바이너리 무수정. 이 카드는 측정 방법의 결함을 바로잡은 기록이다.

## 1. 한 줄 요약

#524 로 크래시를 잡은 뒤에도 BGM 이 심하게 끊겼는데, 그 끊김의 대부분은
**진단용 앱(`audiodbg2`)이 켜 놓은 Wine/GStreamer 추적 로그가 만든 것**이었다.
추적을 끈 프로덕션 구성에서 게스트 오디오 연속성은 9% → 95.5% 로 회복됐다.

## 2. 새 계측 축: 디코드 실시간 배속 (VERIFIED)

지금까지의 지표(비영 샘플 비율, 상관계수)는 "왜" 를 말해 주지 않았다.
게스트 로그의 미디어 타임스탬프를 두 번 읽어 **오디오 시간 / 벽시계 시간** 을 직접 잰다.

```text
T0 19:23:21  pts 0:00:24.267
T1 19:24:01  pts 0:00:29.126
=> 40 초 동안 오디오 4.859 초  =  실시간의 12.1%
```

같은 로그 한 장에서 독립적으로 교차 확인된다. GStreamer 자체 파이프라인 시계가
`0:05:47` 일 때 미디어 pts 는 `0:00:25` 였다.

**디코드가 실시간의 1/8 속도면 버퍼를 아무리 키워도 끊긴다.** 공급이 모자란 것이지
버퍼가 모자란 게 아니다. 상관계수가 0.12 로 "원본 아님" 이 나온 것도 같은 이유다 —
8 배 늘어진 파형은 원본 포락선과 맞지 않는다.

## 3. 런타임 회귀 가설은 기각 (VERIFIED)

#250 은 `callaudio2` 런타임에서 원본 `PetHouse.mp3` 의 자연 루프를 실시간으로 재생했다고
기록한다. 그래서 "이후 JIT 런타임에서 디코드 성능이 회귀했다" 를 첫 가설로 두고
**같은 root·같은 앱에 런타임만 바꿔** 측정했다.

| 런타임 | 디코드 실시간 배속 |
|---|---|
| `boxedwine.upstreamjit64fn6inlineabi2` (현행) | 12.1% |
| `boxedwine.callaudio2` (2026-07-22, #250 의 그 빌드) | **13.5%** |

차이가 없다. **런타임 회귀가 아니다.** 이 한 번의 측정으로 런타임 60여 개를 이분 탐색하는
작업이 통째로 불필요해졌다.

## 4. 진짜 원인 — 관측 장치가 관측 대상을 8 배 느리게 만들고 있었다 (VERIFIED)

`Azrok_D3D9Web_pathouse_guesttexrecycle4_audiodbg2` 의 `run_azrok_audiodbg2.bat` 는
`WINEDEBUG=-all,+seh,warn+module,+quartz` 를 켠다. 게스트 로그에는 GStreamer 자체
디버그도 LOG 레벨로 찍히고 있었다(`wg_allocator.c:292`, `wg_transform.c:1136` 등).
버퍼 하나마다 문자열 포맷팅 + 콘솔 출력이 **에뮬레이션된 코드로** 돌아간다.

같은 8 배가 부팅 시간에도 그대로 나타난다. 이것이 결정적 증거다.

| 앱 | 오디오 노드 등장까지 | 게스트 오디오 비영 샘플 |
|---|---|---|
| `..._audiodbg2` (`+quartz`, GST LOG) | **325 초** | 9% |
| `...guesttexrecycle4` (`run_azrok_web.bat`, 추적 없음) | **40 초** | **95.5%** |

부팅 8.1 배, 오디오 연속성 약 10 배. 두 수치가 같은 배율로 움직인다.

프로덕션 구성 측정값 (211 초 창, `webBgmFallback=0`):

- 오디오 콜백 4,918 회 / 이론값 4,945 회 = **99.5%** — 브라우저 쪽은 정상
- 비영 샘플 8,613,005 / 10,072,064 = 85.5% (BGM 시작 전 무음 23 초 포함)
- BGM 재생 구간만 보면 **95.5%**

**추가 성과**: `run_azrok_web.bat` 은 WINEDEBUG 를 아예 켜지 않는다. #524 이전에는 이 런처로
돌리면 프로세스가 `EXITCODE=-1073741819` 로 죽었다. 이제 죽지 않는다 — pcre2 수정이
프로덕션 구성에서 독립적으로 재확인된 셈이다.

## 5. 남은 잔여 끊김 — 주기적이다 (VERIFIED)

사용자 청취 판정: "끊김 정도가 90% 정도 나아졌다, 완전히 사라진 건 아니다."

60 초 루프백 캡처(10 ms 블록, 임계 -54 dB)의 구멍 구조:

```text
active     : 5908/6000 블록 = 98.5%
구멍       : 30 개, 최장 70 ms, 중앙값 30 ms
20 ms 이상 : 22 개, 합계 0.84 초
구멍 간격  : 중앙값 2,550 ms  (범위 2,370 ~ 3,000 ms)
```

**간격이 균일하다.** 렌더 지터로 인한 일반적 언더런이라면 간격이 무작위(포아송)여야 한다.
2.5 초 주기는 특정 반복 작업이 있다는 뜻이다. 길이 20~70 ms 도 GC/긴 작업 구간과 일치한다.

재생 속도도 함께 쟀다. 캡처를 배속 계수로 훑어 원본 `PetHouse.mp3` 와 맞춰 보면
계수 1.025 에서 상관이 0.2152 → **0.5180** 으로 뚜렷한 봉우리를 만든다.
즉 재생이 약 2.4% 느린데, 이는 구멍 총합 0.84 초 / 60 초 = 1.4% 로 **대부분 설명된다**.
별도의 리샘플링 버그를 가정할 근거는 없다.

상관이 0.52 에 그치는 것은 구멍이 불규칙하게 시간축을 늘려 단일 배속 보정으로는
60 초 창 전체를 정렬할 수 없기 때문이며, 효과음이 섞인 캡처라는 점도 작용한다.
**최고 일치 곡이 `PetHouse.mp3`(= PatHouse 씬의 실제 BGM)로 나온 것 자체가 신호다.**

### 왜 이 구성이 구멍에 취약한가

`-sOFFSCREENCANVAS_SUPPORT=0` 이므로 **WebGL 호출이 전부 메인 스레드로 프록시된다**.
오디오 ScriptProcessorNode 도 메인 스레드에서 돈다. 둘이 같은 스레드를 쓴다.
그리고 여유분이 매우 얇다.

- `platform/sdl/kdspaudio.cpp`: `DSP_BUFFER_SIZE (1024*32)` = 32 KB
  44100 Hz · 2ch · F32 기준 **약 93 ms** 가 게스트가 미리 채워 둘 수 있는 최대치
- `KDspAudioMath::getRequestedSdlPeriodFrames()` = 2048 프레임 = 48 kHz 에서 **42.7 ms**
- `startPlaybackWhenBuffered()` 의 48 ms 는 **최초 시작 문턱값일 뿐** 이후 재버퍼링은 없다

## 6. 잔여 끊김의 원인 — 2.5 초마다 메인 스레드가 100 ms 멈춘다 (VERIFIED)

한 시계 위에서 두 계측을 동시에 돌렸다. 25 ms `setInterval` 샘플러(간격이 벌어지면
메인 스레드가 막힌 것)와 오디오 콜백별 비영 샘플 기록이다.

```text
메인 스레드 정지 (>=60ms):  13 회 / 31.9 초
  t=1851 105ms, 4255 100ms, 6726 92ms, 9025 112ms, 11400 99ms, 13800 101ms,
  16176 97ms, 18576 95ms, 20950 94ms, 23250 88ms, 25951 99ms, 28550 87ms, 31375 126ms
  간격 중앙값 약 2,400 ms

드롭아웃 7 건 중 메인 스레드 정지와 일치: 7/7
드롭아웃 7 건 중 힙 증가와 일치      : 0/7   (측정 구간 힙 증가 0 회)
```

재현성도 확인했다. 다른 구간에서 다시 재도 16.8 초에 7 회, 간격 2,421~2,874 ms,
길이 89~149 ms 로 같았다.

드롭아웃은 거의 항상 **정확히 콜백 1 개(43 ms)** 이고, 그동안 Present 는 0 이다.
즉 오디오만의 문제가 아니라 **게스트 전체가 함께 멈춘다**.

### 무엇이 멈추는가

- `longtask` 옵저버: 316 초 동안 **0 건**. `PerformanceObserver.supportedEntryTypes` 에
  `longtask` 가 있고 `crossOriginIsolated=true` 이므로 옵저버 자체는 유효하다.
  → 긴 **JS 태스크** 는 없다.
- `long-animation-frame`: 92~107 ms 짜리 프레임이 다수인데 `blockingDuration=0`,
  `scripts=[]`, `render=0`, `style=0`. 스크립트/스타일/렌더 어디에도 귀속되지 않는다.
- 예외적으로 한 건만 스크립트가 붙었다: **`IDBRequest.onsuccess` 129 ms**.

`boxedwine-shell.js` 는 게스트 파일시스템을 `FS.mount(IDBFS, {autoPersist: true}, ROOT)`
로 올린다. 게스트가 파일을 쓰면 IndexedDB 동기화가 걸린다. Wine 은 레지스트리를
주기적으로 flush 하므로 2.5 초 주기의 쓰기가 발생할 여지가 있다.

**검증 수단은 재빌드가 필요 없다.** 같은 셸이 URL 파라미터를 받는다:

```text
&storage=memory     ->  Config.storageMode = STORAGE_MEMORY, IDBFS 마운트 자체를 건너뜀
```

### FPS 관측 (NOT VERIFIED — 별도 확인 필요)

같은 세션에서 Present 율이 **34.2~34.6 fps** 로 일정했다. 목표 50 fps 에 못 미친다.
BGM 이 살아나면서 디코드 부하가 새로 들어온 영향인지, 씬/조건이 다른 것인지는
아직 가르지 않았다. #497 기준선과 같은 조건으로 다시 재야 한다.

- `platform/sdl/kdspaudio.cpp`: `DSP_BUFFER_SIZE (1024*32)` = 32 KB
  44100 Hz · 2ch · F32 기준 **약 93 ms** 가 게스트가 미리 채워 둘 수 있는 최대치
- `KDspAudioMath::getRequestedSdlPeriodFrames()` = 2048 프레임 = 48 kHz 에서 **42.7 ms**
- `startPlaybackWhenBuffered()` 의 48 ms 는 **최초 시작 문턱값일 뿐** 이후 재버퍼링은 없다

즉 메인 스레드가 한 번 ~50 ms 이상 멈추면 그대로 구멍이 난다. 50 fps 렌더 루프의
프레임 예산이 20 ms 이므로 여유가 두 콜백 남짓밖에 없다.

다만 2026-07-22 에 이 파라미터 공간은 이미 한 차례 훑은 흔적이 있다
(`upstreamjit8audioprebuffer`, `9period2048`, `10queue96`, `12audio64k`,
`15audiofrag8192`, `14audiobest`, `17release`). 현재 값이 그때의 튜닝 결과다.
그때와 달라진 조건은 **게임이 50 fps 로 돌면서 메인 스레드 부하가 커졌다**는 점이다.

다음 단계는 잔여 구멍의 **길이 분포**를 재는 것이다. 구멍이 40~100 ms 규모로 흩어져 있으면
여유분 문제이고, 수백 ms 단위면 다른 원인이다. 재기 전에는 늘리지 않는다.

## 6.5 계측 축 선택 — 루프백은 시스템 상태에 오염된다

WASAPI 루프백(`tools/capture_loopback.py`)은 시스템 믹서 뒤에서 녹음하므로
**브라우저를 음소거하면 전부 무음으로 잡힌다.** 사용자가 음소거한 구간의 루프백 수치와
원본 상관 대조는 무효다. 같은 이유로 다른 앱의 소리도 섞인다(이 프로젝트에서 이미
한 번 오염된 적이 있다).

게스트 탭(SDL `scriptProcessorNode.onaudioprocess` 에서 읽는 PCM)은 OS 믹서 **앞단**이라
음소거와 무관하고 다른 앱 소리도 섞이지 않는다. 드롭아웃 개수·콜백률·Present 율은
전부 이 축으로 잴 수 있다. **원본 곡과의 상관 대조가 필요할 때만 루프백을 쓰고,
그때는 음소거 여부를 먼저 확인할 것.**

## 7. 방법론 교훈

`+quartz` 와 GST 디버그는 #524 에서 널 디스패치 지점을 찾는 데 반드시 필요했다.
그런데 그 뒤 **성능 성격의 질문에 같은 계측 앱을 그대로 재사용한 것**이 오진의 원인이었다.
진단용 빌드는 원인 규명이 끝나는 즉시 내려놓아야 한다.

같은 실수가 이 프로젝트에서 두 번째다. #524 §5 는 계측용 root 가 GLib 심볼 불일치로
스스로 로드되지 못해 추적이 한 줄도 안 나왔던 사례다. **계측 장치는 그 자체가
검증 대상이다.**

## 7. 재현

```text
root  = TinyCore15Wine11.0-wsaeventfix5-korean4-bgmloop3-dsound80ms1-pcrestd1
app   = Azrok_D3D9Web_pathouse_guesttexrecycle4      (진단 앱 아님)
p     = run_azrok_web.bat                            (WINEDEBUG 미설정)
URL   += &webBgmFallback=0                           (브라우저 대행 재생 끔)
```

디코드 배속을 재려면 `audiodbg2` 가 필요하지만, 그 숫자는 **추적이 켜진 상태의 배속**임을
반드시 함께 적을 것. 프로덕션 배속은 이 방법으로는 잴 수 없다.
