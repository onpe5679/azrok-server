# Runtime Patches And Telemetry

## What `azrok_server.py` Currently Does

- hooks `connect()` to force `127.0.0.1:9000`
- runs the local TCP server
- emulates the early login/loading protocol
- patches selected client runtime paths
- polls key runtime fields and prints `[STATE]` lines

## Acknex / 3D GameStudio Notes

Official manual facts that matter for the current investigation:

- `acknex.wdf`
  - is the starter window definition file
  - is generated by the Publish dialog `Starter` option from a `WINDOW`
    definition
  - is interpreted by the engine at startup before the main script is read
- `E1515`
  - is the engine's generic `Invalid arguments` family
  - it is not the same bucket as missing-file / bad-level errors
- `WRS`
  - is the compressed/encrypted game resource container
  - all `WRS` resources in the work folder are automatically opened at engine
    start
- `ent_create` / `ent_createlocal`
  - create entities from filenames or `NULL`
  - `ent_createlocal` is local-only and still uses normal engine resource
    loading rules
- `level_load`
  - purges the level entity-file cache on level change
  - `last_error` becomes valid one frame later and counts missing entities
- `preload_mode`
  - controls whether entities, meshes, textures, and environment light are
    created earlier or later

Current interpretation:

- when the client shows `Error E1515 / Invalid arguments in acknex.wdf` during
  the loading phase, that does not necessarily mean the engine is literally
  parsing `acknex.wdf` at that moment
- in the current reverse-engineered path, the more plausible meaning is a
  generic engine-side invalid-argument fault while local scene/resource setup is
  running
- this matches the latest crash family around missing named scene assets such as
  `sky_MDL_325`
- it also fits the current Plaza scene bootstrap path better than a literal
  broken `acknex.wdf` file

## Active Runtime Patches

Important default:

- popup hard-bypass patches are now disabled unless
  `AZROK_POPUP_HARD_BYPASSES=1`
- this is intentional because `CPopupLoading` appears to own the baked loading
  screen itself, so skipping popup finalize/teardown can block the real exit
  path

### Dispatch Flag Bypass

- patch at `0x591DC7`
- keeps packet dispatch enabled

### State-1 `0x0064` Null-Entity Guard

Purpose:

- intercept the early null self-entity case inside `HandleS2C_0064_ApplyAuthoritativeSelf (0x00615650)`

Current guard behavior:

1. log `gm`
2. increment `opcode100_hits`
3. if the self entity is already present, resume the normal path
4. if it is missing:
   - increment `self_init_hits`
   - set `ECX = gm`
   - call `FUN_0050B400(0x6E)`
   - rewrite the singleton self actor id from the authoritative `S->C 0x0064`
     packet id
   - continue on the safe skip path

Important caution:

- `FUN_0050B400(0x6E)` is the internal local scene bootstrap dispatcher
- it is not the same as sending network packet `0x006E`

### Scene Sky Null Guard

Purpose:

- stop the local `0x6E` bootstrap from crashing when `FUN_006084A0` cannot find
  `sky_MDL_325` yet

Current guard behavior:

- intercept `0x006084CA`
- if `sceneObj+0x39` is still null after `ent_for_name("sky_MDL_325")`,
  skip the remaining sky-tail writes and continue

### Scene Water/Sound Null Guard

Purpose:

- stop stage-4 local scene setup from calling `ent_playloop(entity, sound, 100)`
  with a null entity or null sound handle

Current guard behavior:

- intercept `0x0060E8E6`
- preserve the original `ent_for_name` / `snd_create` stores
- if either cached input is null, skip `ent_playloop` and store `0` as the loop
  handle

### State-1 Tail Close Guard

Purpose:

- keep the final loading-close handoff alive after the local bootstrap succeeds
- stop the late crash at `0x006159EC`

Current guard behavior:

- intercept the tail at `0x006159E9`
- avoid the original:
  - `mov eax, [ebp-4]`
  - `mov ecx, [eax+4]`
  - `call thunk_FUN_0050A840`
- load `ECX` from the already logged `gm` instead
- if `gm` was never captured, skip the close call and return safely

Reason:

- recent telemetry shows the self singleton can now exist with `self id = 1`
- the next failure is the final wrapper reacquire just before popup close
- `FUN_0050A840()` is still desirable because it ultimately drives the popup
  object toward `+0x9C = 1`

### Popup Hard Bypasses

Current status:

- default off
- opt-in only with `AZROK_POPUP_HARD_BYPASSES=1`

Covered patches:

- popup close safe stub
- popup child null latch
- popup update gate
- popup finalize vcall skip
- popup teardown skip

Reason:

- these were useful while the client was crashing before or during the loading
  popup close path
- now that the loading screen is understood to be the popup itself, these
  patches are too invasive to leave on by default
- conservative guards such as scene null checks and late vcall guards remain
  active


### Scene Stage-6 Vcall Guards

Purpose:

- stop post-close scene/bootstrap code from calling near-null or invalid virtual
  method targets after `popup+0x9C = 1`

Current guard behavior:

- intercept four stage-6 virtual-call sites:
  - `0x006147A5`
  - `0x0061481D`
  - `0x0061485D`
  - `0x006148F9`
- validate:
  - object pointer from `[ebp-0x48]`
  - vtable pointer
  - method target at vtable `+4`
- if the target is below `0x00010000`, skip the call instead of jumping into a
  near-null address such as `0x00000002`

### Scene Wrapper Vcall Guards

Purpose:

- catch the second wave of near-null virtual calls that happen through helper
  wrapper functions instead of direct `CALL EDX` sites

Current guard behavior:

- intercept wrapper-call sites that share the same virtual dispatch pattern:
  - `0x005CE010`
  - `0x005FC034`
  - `0x005F38C0`
  - `0x005F2120`
- validate:
  - wrapper `this` pointer from `[ebp-4]`
  - wrapper vtable pointer
  - method target at vtable `+4`
- if the target is below `0x00010000`, skip the virtual call and emulate the
  skipped callee cleanup with `add esp, 4`

Reason:

- stage 6 does not only dispatch through the four explicit object calls at
  `0x006147A5/0x0061481D/0x0061485D/0x006148F9`
- it also reaches helper wrappers such as:
  - `FUN_005fbfd0`
  - `FUN_005f38b0`
  - `FUN_005f2110`
- these wrappers still resolve `(*this)->vtable[1]` and can produce the same
  `unknown+0x00000002` crash family if their method target is near-null

### Scene Post-Load Ready Latch Force

Purpose:

- flip the native post-load ready latch when the scene wrapper owner is valid
- align runtime state with the new telemetry finding that loading can advance
  to `stage=9#10` and `popup+0x9C = 1` while the latch still stays zero

Current guard behavior:

- intercept `0x00614547`
- recover the scene wrapper owner from `[ebp-4] -> +4`
- if the owner pointer is sane, write `1` to `owner + 0x31946`
- set `EAX = 1` before resuming the original flow

Reason:

- current telemetry prints this field as:
  - `gate(owner=..., latch=...)`
- the best recent runs still end with:
  - `stage=9#10`
  - `popup+0x9C = 1`
  - `self id = 1`
  - `self ready = 1`
  - `gate(..., latch=0x00000000)`
- that makes the ready latch the strongest remaining native loading-exit gate

### Popup/UI Child-State Null Guard

Purpose:

- stop next-screen confirm popups from crashing when an optional child widget
  behind `this+0x3d` is still missing

Current guard behavior:

- replace `FUN_0051b0e0`
- preserve the original visible state writes:
  - `this+0x5c = 0`
  - `this+0x4e = incoming_flag`
- write `0` or `0x4000` to `child+0x1c` only if `child = *(this+0x3d)` is
  non-null

Reason:

- the newest live report is:
  - loading now advances to the next screen
  - clicking the visible confirm popup immediately crashes
- the matching crash site is:
  - `Azrok.exe+0x0011B110`
  - `VA 0x0051b110`
  - `mov dword ptr [ecx+0x1c], 0`
  - `ecx = 0`

## Reading `[STATE]` Quickly

- `hits=1/0`
  - `0x0064` guard fired, no local bootstrap attempt yet
- `hits=1/1`
  - guard fired and local bootstrap attempt ran once
- `stage=6#...`
  - local bootstrap reached the heavy post-close scene stage
- `stage=7#...` or higher
  - the stage-6 family returned and the failure moved later
- `self id != 0` with `ent=0`
  - self id latched, singleton still missing
- `self id != 1` with `ent!=0`
  - local bootstrap created the singleton, but authoritative actor-id
  reconciliation may still be lagging
- `self id = 1` with `ent!=0`, `ready=1`, `model=00/00`
  - self singleton exists and actor id is reconciled
  - the next blocker is likely scene/environment setup, not the old self-null
    phase
- `ready=0` with `model=FF/FF`
  - native local setup did not reach model/entity creation
- `popup+0x9C = 1`
  - close request ran
- `popup+0x9C = 1` with `self id = 1`, `ent != 0`, `ready = 1`
  - strong sign that the client reached late loading close
  - not enough by itself to declare true gameplay
- `popup+0x9C = 0` after a close attempt
  - popup tick consumed or reset the close latch
- `0x002159EC` with `popup+0x9C = 0`
  - the loader died immediately before or during the final close handoff

## Packet-First RE Notes

High-confidence packet observations from the current Ghidra pass:

- first `S->C 0x0007` is not just passive state loading
  - it also reaches the secondary transition path
  - that path can open local loading with code `100`, `0x6e`, or `0x6f`
- `S->C 0x0005` and `S->C 0x0007` both write the same local state field via
  `FUN_0059e300`
- `0x0007` tail bytes `0x1D4..0x1D7` feed directly into
  `SendC2S_0064_LocalBootstrapStatus (0x006130B0)` bootstrap slot handling

Practical consequence:

- the current runtime patch stack is useful for crash discovery
- but the highest-value next work is packet reconstruction, especially:
  - `0x0007`
  - `0x0005`
  - `0x0010`
  - `0x0011`

## 2026-03-30 Packet-First Addendum

- `0x0007 byte1` and `byte2` are now known to participate directly in the
  natural local bootstrap path.
  - they eventually seed `player+0x9D` and `player+0xA1`
- `0x0007 +0x07` and `0x0005[2:6]` both write the same manager-side state word
  through `FUN_0059E300`.
- packet-first reconstruction therefore needs to treat:
  - `0x0007 byte1` as selected character/species input
  - `0x125..0x12F` as live one-byte command fields, not harmless zero padding

## 2026-03-30 Protocol-First Notes

- `S->C 0x0007` now has one newly confirmed builder bug:
  - `+0x125..+0x12F` must not be treated as a zero-filled empty region
  - native code feeds those 11 bytes directly into `DomainCode_EmitLocalEffect (0x0059A6E0)`
  - `0xFF` is the safer no-op sentinel than `0`
- `S->C 0x0005` is more meaningful than its size suggests:
  - subtype `0x13` can flush queued internal progression work
  - subtype `0x00` only updates the shared state dword
- `S->C 0x0010` and `0x0011` should now be treated as real keyed/global table
  inputs during packet reconstruction, not mere cosmetic fillers
