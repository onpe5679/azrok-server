# 놀이·마술·체육 미니게임 엔진 + 봉에너지 게이트 (2026-07-18)

정적 분석(Ghidra, `Azrok_original.exe`). 놀이(0x65)·마술(0x67)·체육(gym 0x66) 미니게임이 **단일 공유
리워드 엔진**을 타고, 스킬 적립이 **봉에너지(stat9) 게이트**에 걸리는 것을 확정. **핵심 게이트
FUN_005a4ba0은 Claude 본인 디컴파일로 재검증**(에이전트 보고와 바이트 일치). VERIFIED=디컴파일/read_memory,
INFERRED=추론.

## ★ 1. 봉에너지(stat9) 게이트 — 게임 메시지의 코드 구현 (VERIFIED, 본인 재검증)

`FUN_005a4ba0`(범용 스탯 write executor, content/69) 서두 게이트:
```c
// statbase = *(logic+0x5f4), 스탯 stride 0xc, stat9 = +0x6c
if ( ( (statbase[0x6c] != 0)                              // 봉에너지(stat9) != 0
       || (idx != 2 && (idx < 0x1f || 0x27 < idx)) )      // OR (idx≠2 AND idx∉[31..39])
     && (-1 < idx) && (idx < 0x47) ) {                    // AND 0 ≤ idx < 71
    statbase[idx*0xc] += delta;   // max클램프(FUN_005a4a50) → min클램프(+4)
}
```
- **봉에너지(stat9)==0 이면 경험치(stat2)와 스킬 스탯(31~39: 팔굽/아령/줄넘기/저글링/요요/덤블링/매직클/퍼니쉴/에어훅)
  적립이 전면 차단됨.** 그 외 스탯(허기/위생/청소도 등)은 정상 write.
- ★ 이것이 게임 화면 메시지 **"봉에너지가 0이 되면 활동을 해도 경험치가 오르지 않습니다"의 정확한 코드 구현.**
  메시지-only 였던 주장을 디컴파일 본문으로 VERIFIED. (content/71 §3 봉에너지=성장핵심자원 가설 확증.)
- **stat9 = 봉에너지 확정** (lgc.tmp stat[9]=봉에너지 max300, 9×0xc=0x6c 오프셋 일치). 에이전트가 x32dbg 필요·"nexus
  스탯 가능성"으로 남긴 것을 정적으로 해소 — nexus 아님, 봉에너지임.
- 스킬 상한 450 = max클램프(FUN_005a4a50), 하한 = 스탯레코드 +4(min 필드).

## ★ 5. 액션코드 → 스킬스탯 매핑 (VERIFIED-read_memory DAT_006e07d0, 26엔트리) — 서버 계약 핵심

```
놀이: 0xE4/E5/E6→stat34(저글링)  0xE7/E8/E9→stat35(요요)   0xEA/EB/EC→stat36(덤블링)
마술: 0xED/EE/EF→stat37(매직클)  0xF0/F1/F2→stat38(퍼니쉴)  0xF3/F4/F5→stat39(에어훅)
gym : 0xF6/F7→stat31(팔굽)        0xF8/F9/FA→stat32(아령)    0xFB/FC/FD→stat33(줄넘기)
```
- **독서 domain0**: action 500, item 0xffffffff. 7번째 벡터=**stat30(지식) 그대로**(리매핑 없음). 베이스 델타
  (DAT_006dff38 실측): 허기-10/위생-5/에너지-5/재미-5/스트레스+5/봉에너지-5/**지식경험+5**(+난이도 티어). 공부라 재미 -5.
- **요리 domain1**: room 0x68(cook) 활동완료 시. 7번째 리매퍼 = `FUN_005a8aa0`(테이블 &DAT_006e0e70 33엔트리, 본인 재검증)
  = **조리 음식id → 요리숙련스탯**: 1006→40(토스트)…1020→54(김밥), 1001-1005→stat29(인스턴트), 1000→-1. (content/77 blocker 해결.)
- 도메인 **2/3/4**는 출력 플레이스홀더 stat30(0x1e)을 `FUN_005a26a0(action_code)`으로 스킬 스탯(31-39)에 리매핑.
  즉 **7번째 벡터 = 도메인별 대상 스탯**(d0=지식30 · d1=요리40-54 · d2/3/4=스킬31-39).
  반응 애니 게이트 `FUN_00597de0`의 case그룹(0xe4-ec/0xed-f5/0xf6-fd)과 일치.
- 리워드 벡터 DAT_006e07b0 = [stat3,stat4,stat5,stat6,stat7,stat9,스킬]. 놀이 기본델타 stat3-10/stat4-5/stat5-5/
  stat6+5/stat7-5/stat9-5/스킬+5. 마술 stat3-5/stat4-5/stat5-5/stat6+5/stat7 0/stat9-5/스킬+5.
  → **운동/놀이/마술은 봉에너지(stat9)를 소모(-5)하면서 스킬+5.** 봉에너지 0이면 §1 게이트로 스킬 안 오름.

## 5.5 리워드 공식 = 베이스 + 티어 가산 (VERIFIED, 5도메인 완전 디코드)

`최종델타[s] = 헤더 베이스[s] + Σ(각 행의 티어블록[s])`, 이후 floor 클램프, 7번째만 대상스탯 리매핑 적용. **배수 아님, 가산.**
- **5도메인 헤더/행 테이블**(read_memory 실측): d0독서 DAT_006dff38/90(3행) · d1요리 DAT_006e0140/198(4행) · d2gym DAT_006e03d8/430(2행) · d3마술 DAT_006e0550/5a8(1행) · d4놀이 DAT_006e0638/690(2행).
- **베이스 7스탯 벡터**[허기,위생,에너지,재미,스트레스,봉E,대상]: d0 `-10,-5,-5,-5,+5,-5,+5`(★독서만 재미-5/스트레스+5=공부는 재미없고 스트레스) · d1 `-5,-5,-5,0,0,-5,+5` · d2 `-10,-5,-5,+5,-5,-5,+5` · d3 `-5,-5,-5,+5,0,-5,+5` · d4 `-10,-5,-5,+5,-5,-5,+5`. **모든 도메인 대상스탯 베이스=+5 공통.**
- **티어**: 각 행의 selector 스탯 현재값(`FUN_005a49b0` 리더)으로 선택 — <20 tier0 / <40 t1 / <60 t2 / <80 t3 / <100 t4 / ≥100 무기여. 행=0x90B=[selector 4B]+[5티어×7int]. 예) 독서 행0 selector=stat7(스트레스): 스트레스 높을수록 지식획득 -1/-2/-3 페널티+소모↑ (스트레스<40이면 페널티 0).
- **두 리매퍼**: 요리 `FUN_005a8aa0`(음식id→stat40-54, §5) · 운동/마술/놀이 `FUN_005a26a0`(테이블 DAT_006e07d0, actionCode 0xe4-0xfd→stat31-39). 독서(d0)는 리매핑 없이 대상=stat30 직접.
- **상호 배타**: 지식30=오직 d0, 요리40-54=오직 d1, 스킬31-39=오직 d2/3/4. 겹침 없음.

## 6. 패킷 유무 (VERIFIED, 79에서 동적 교정)

> **SUPERSEDED by 79.** "진행·리워드 경로에 전송 전혀 없음"은 틀렸다.
- 리워드 계산 자체는 로컬이지만 완료 직후 `FUN_005a4770(0,1,7)` → C→S `0x0007` 196B 상태 저장이 발생한다.
- Gym 아령 두 번에서 C→S #472/#492와 stat32 `0→8→16`을 x32dbg/packet으로 직접 확인했다.
- ⚠ gym의 C→S 0x0E(content/66)는 **"gym-item 소모품 아이템 사용"**(FUN_00596690의 0xd1/0xd4 인벤토리 경로)이지,
  스킬 연습 리워드가 아님 — 두 경로 혼동 주의.

## 7. 서버 재구현 계약

- 리워드 공식·티어·액션코드 매핑은 클라이언트 상수이므로 서버가 보상을 계산할 필요는 없다.
- 서버는 완료 직후 C→S `0x0007` 저장을 받아 **stat31-39(스킬 max450), stat3/4/5/6/7/9**를 보존하고,
  재접속 S→C `0x0007`에 정확히 복원해야 한다. stat9는 다음 보상의 게이트값이다.
