# Azrok Plaza (아즈록 플라자) 리버스 엔지니어링 분석 요청서

## 1. 프로젝트 개요

**게임**: 아즈록 플라자 (Azrok Plaza)
**개발사**: 한솔교육 (2006~2008년경)
**장르**: 어린이용 교육 온라인 게임
**현황**: 서버 폐쇄로 플레이 불가

**목표**: 로컬 TCP 서버 에뮬레이터를 만들어 오프라인에서 게임을 다시 플레이할 수 있게 하는 것

## 3. 현재까지 수행한 작업

### 3.1 IAT Hooking (완료)
- Entry Point Stomping 기법으로 `connect()`를 후킹
- 모든 서버 접속을 `127.0.0.1:9000`으로 리다이렉트
- Python TCP 서버에서 패킷 수신/응답 처리

### 3.2 런타임 바이너리 패치 (완료)
- **VA 0x591DC7**: 패킷 디스패치 함수의 플래그 체크 우회 (`JZ +0x16` → `NOP NOP`)
- 이 패치 없이는 서버에서 보낸 패킷이 처리되지 않음

### 3.3 프로토콜 분석 (부분 완료)

**패킷 프레임 포맷**:
```
[2바이트 LE payload_size][2바이트 LE opcode][payload...]
```
- TCP 스트림에서 여러 패킷이 하나의 recv()에 합쳐져 올 수 있음
- 내부 패킷 큐: 300 슬롯 × 169바이트(0xA9), `this+0x9360` 위치
- 슬롯 포맷: `[1B occupied][4B opcode][4B size][payload...]`

## 4. 발견한 내부 구조

### 4.1 패킷 처리 흐름
```
TCP recv → 디스패치 함수 (VA 0x591DA0)
  → 플래그 체크 (this+0x4076) [NOP 패치로 우회함]
  → enqueue (VA 0x591E00) → 링 버퍼에 저장

메인 스레드:
  dequeue (VA 0x591F90) → 래퍼 (VA 0x592650)
  → 프로세서 (VA 0x593E40)
  → this->vtable[3](opcode, payload_ptr, payload_size) 호출
```

### 4.2 vtable 구조 (VA 0x6A6150)
| 인덱스 | VA | 설명 |
|---|---|---|
| [0] | 0x6C1B54 | (데이터 포인터?) |
| [1] | 0x593C90 | 함수 |
| [2] | 0x593E40 | 메인 스레드 프로세서 (dequeue + dispatch) |
| [3] | 0x5927D0 | **패킷 핸들러 - 현재 STUB** |

### 4.3 핵심 문제: vtable[3] (VA 0x5927D0)이 STUB
```asm
push ebp
mov ebp, esp
sub esp, 0x44
push regs
mov [ebp-4], ecx    ; this 포인터 저장
pop regs
leave
ret                  ; ← 아무 것도 안 하고 리턴
```
- 서버에서 보낸 패킷이 큐에 들어가고 디큐되어 이 함수까지 오지만, 함수 자체가 아무 동작도 하지 않음
- **그럼에도 불구하고** 특정 opcode 조합을 보내면 게임이 반응함 (아래 참조)
- vtable[3]이 스텁인데도 게임이 반응하는 이유를 분석해야 함

## 5. 알려진 opcode 목록

### 5.1 클라이언트 → 서버 (게임이 보내는 패킷)
| Opcode | Payload 크기 | 설명 |
|---|---|---|
| 0x0000 | 106B | 최초 접속 시 Hello 패킷 |
| 0x0001 | 0B | 상태 신호? (캐릭터 생성 후 발생) |
| 0x0004 | 15B | 캐릭터 생성 요청 |
| 0x0007 | 196B | 맵/존 데이터 요청? (캐릭터 생성 후 발생) |
| 0x0016 | 1B | 하트비트 (주기적, payload=0x00) |
| 0x0017 | 6B | 캐릭터 생성 후 발생 |

### 5.2 캐릭터 생성 패킷 (opcode 0x0004) 상세
```
Payload 구조: [1B species_type][14B name_euckr_padded]
  - species_type: 0=뮤리, 1=새지(?), 2=아링(?), 3=테로
  - name: EUC-KR 인코딩, 나머지 0x00 패딩
```

### 5.3 opcode 0x0007 (196B) 패킷 예시
```
0000: 00 00 00 00 00 FF 00 00 00 00 00 00 00 00 00 00
0010: (이후 전부 0x00 ... 총 196바이트)
```
- byte[4] = 0xFF, 나머지 전부 0x00

### 5.4 opcode 0x0017 (6B) 패킷 예시
```
Payload: 07 01 00 00 00 00
```
- 첫 바이트 0x07이 opcode 0x0007과 관련 있을 가능성

## 6. 서버 → 클라이언트 응답 실험 결과

캐릭터 생성(0x0004) 수신 후, 서버에서 다양한 opcode 조합을 보내본 결과:

| 서버 응답 opcode | 결과 |
|---|---|
| 0x0004 (1B 또는 44B payload) | 무반응, 캐릭터 생성 화면 유지 |
| 0x0005 단독 | 무반응 |
| 0x0001 단독 | "연결이 종료되었습니다" → 즉시 게임 종료 |
| 0x0002 + 0x0003 | 게임이 0x0007, 0x0001, 0x0017 전송 후 종료 (에코 때문) |
| 0x0002 + 0x0003 (0x0001 에코 안 함) | **로딩 화면 진입! 하트비트 유지. 로딩에서 멈춤** |
| 0x0004+0x0000+0x0001+0x0002+0x0003+0x0005 (전체) | 로딩 화면 진입 후 종료 |

### 현재 상태: **로딩 화면에서 멈춤**

동작하는 시퀀스:
```
서버 ← 게임: 0x0004 (캐릭터 생성)
서버 → 게임: 0x0002 (payload: 0x01) + 0x0003 (payload: 0x01)
서버 ← 게임: 0x0007 (196B), 0x0001 (0B), 0x0017 (6B)
서버 → 게임: 0x0007 (0x01), 0x0017 (0x01), 0x0005 (0x01)
  → 이후 하트비트만 반복, 로딩 화면에서 진행 안 됨
```

## 7. 분석 요청 사항

### 7.1 최우선 과제
1. **vtable[3] (VA 0x5927D0)이 스텁인데도 게임이 opcode에 반응하는 메커니즘 규명**
   - 별도의 패킷 처리 경로가 존재하는지?
   - recv() 콜백에서 직접 처리하는 코드가 있는지?
   - vtable이 런타임에 교체되는지?

2. **로딩 화면을 통과하기 위해 서버가 보내야 하는 데이터 규명**
   - opcode 0x0007에 대한 올바른 응답 포맷
   - opcode 0x0017에 대한 올바른 응답 포맷
   - 로딩 완료를 위해 필요한 추가 opcode가 있는지

3. **전체 서버→클라이언트 opcode 목록 및 페이로드 구조**
   - 각 opcode가 클라이언트에서 어떻게 처리되는지
   - 필수 필드와 올바른 값

### 7.2 추가 요청
4. **게임 상태 머신 분석**
   - 로그인 → 캐릭터 선택 → 로딩 → 게임 플레이 각 단계에서의 필수 opcode 흐름

5. **맵/존 데이터 구조**
   - 0x0007의 196B payload가 어떤 데이터를 담고 있는지
   - 서버가 보내야 할 맵 데이터 포맷

6. **Winsock 관련 코드 전체 분석**
   - `send()`, `recv()` 호출 위치와 전후 처리 로직
   - 수신 데이터가 어떤 경로로 게임 로직까지 전달되는지
